# Private staging monitoring: production promotion (NOT APPLIED)

The running configuration remains `koipond_stage`, environment `staging`, dashboard `Koipond · Staging`. No production targets, tokens or alerts have been activated. Production cutover requires the user's explicit approval and successful migration tests.

1. Confirm the production release and database restore, both web instances on apps01 ports 3200/3201, workers, backups and readiness. Do not change Vercel or cloud Supabase during preparation.
2. Back up the current monitoring configuration and Grafana database using the existing installer workflow. Record current target health and production rollback release.
3. During the approved promotion, the private edge host `koipond-stage.kluge-it.tech` keeps its private IP, valid TLS and source allowlist. Its fixed `/api/internal/metrics/instance1` and `/instance2` paths must be routed to the production instances on 3200/3201; `/health/ready` must point to that same release. Confirm the ingress owner has made this change before replacing the monitoring token.
4. Read the production monitoring token from the controller's protected `recovery/koipond/production-env-prepared.vault`, using the existing Vault helper. Confirm its JSON shape with the environment owner; never fall back to the staging token or print either token. Atomically replace only `/etc/prometheus/koipond-stage/monitoring.token` (root:prometheus,0640). The directory name is a private implementation detail and can remain unchanged.
5. Prepare reviewed copies of all six monitoring artifacts: rename scrape job `koipond_stage` to `koipond_production`, replace all `environment="staging"` selectors and static labels with `production`, title the existing dashboard `Koipond · Production`, update readiness metric labels, and change stage-only alert descriptions. Preserve the existing dashboard UID/alert UIDs for stable links and a single alert set. Update the installer ownership/job matching and verifier together, explicitly removing the old staging job; do not add a second set of active alerts.
6. Keep the two fixed instance paths and instance labels web1/web2. Keep aggregate SQL metrics deduplicated with `max`; sum per-instance HTTP requests and histogram buckets. Never sum active-user or queue snapshots across replicas.
7. Run `promtool check rules` and `promtool check config`, validate provisioning YAML/JSON and systemd units, then apply only the reviewed configuration. Reload Prometheus; restart Grafana only if its owned alert provisioning changed. Reuse `homelab-telegram` and all existing exporters.
8. Verify both authorized scrapes return instrumentation=1 and healthy targets, readiness=1 and fresh probe timestamps, the production backup metrics are scoped and labelled correctly, dashboard loaded, all unrelated targets/alerts preserved and no duplicate alerts. The existing backup metrics currently describe the new self-hosted staging stack; do not relabel them as production without verifying the production backup owner.
9. Roll back ingress routing, token and all owned monitoring artifacts together from the protected pre-promotion backup if health fails. A production token must never be sent to staging or an arbitrary probe URL. Retain the old production service until the approved rollback window ends.

This document is a preparation checklist, not a runnable promotion flag. The existing installer deliberately remains staging-only, preventing an accidental production token or route switch during routine CI.
